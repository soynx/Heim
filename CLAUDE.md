# Heim — notes for AI agents

Heim is a self-hosted dashboard, a Heimdall alternative. Each widget is a **service** with **multiple links** (public, domain, hostname, IP, VPN…). The user-facing description is in `README.md`.

## Stack and running
- Java 21, Spring Boot 3.5, Maven. One jar (`target/heim.jar`), port **8000**.
- No database. All state lives in `$HEIM_DATA_DIR` (default `./data`; `/data` in Docker): `config.json`, `config.json.bak`, `icons/`, `uploads/`.
- `mvn -q -B test` runs everything (no network needed). To run locally: `java -jar target/heim.jar --server.port=18080` with `HEIM_DATA_DIR` set to a temp directory.
- Docker: a multi-stage `Dockerfile`. `docker-entrypoint.sh` chowns `/data` to `PUID:PGID` (default 1000) and drops root via su-exec. `.dockerignore` keeps `.design/` and `.claude/` out of the build context. `HEIM_RESET_AUTH=true` clears the login credentials at startup.
- Work on feature branches. Commit messages are plain, with no AI co-author trailers.

## Package layout (`dev.soynx.heim`)
| Package | Role |
|---|---|
| `config` | `ConfigStore` (the single owner of `config.json`), `ConfigRepair` (invariants), `migration/` (`schemaVersion` chain), `model/`, `DataPaths`, `IdGenerator` |
| `service` | Business logic: `ServiceManager`, `TabManager`, `SettingsManager`, `Membership`, `UploadStorage`, `Urls` |
| `api` | Thin REST controllers. Data shapes go in `api/dto` (never expose model classes that hold secrets) |
| `probe` | Server-side HTTP health checks per link, plus SSE (`StatusBroadcaster`) |
| `icon` | Icon sources (favicon / library / url / upload), cache in `icons/`, SVG sanitizing |
| `security` | Session login, dynamic view/edit authorization (`AccessPolicy`, `DynamicAuthorizationManager`), SPA-friendly CSRF |
| `backup` | Zip export/import |
| `net` | Shared outbound-HTTP helpers (`TrustAllTls` for `ignoreTls`) |
| `error` | `NotFoundException`, `BadRequestException`, `RevisionConflictException` → JSON `{error, message}` via `ApiExceptionHandler` |

## Core data decisions (don't break these)
- **Tabs = tags = boards.** It's one concept. A service appears on every tab it's in. There is exactly one `isDefault` tab, and a `showAll` tab also lists services that aren't assigned to it.
- **Membership has one source of truth: `tab.groups[].serviceIds`.** Services keep no tab list; `ServiceDto.tabIds` is computed from the tabs. Each tab has its own order. `groups[]` is there for future section headings; v1 uses a single unnamed group.
- Services sit in a flat list and are referenced by ID only. IDs are stable and prefixed (`svc_`, `lnk_`, `tab_`, `grp_`), generated by `IdGenerator`.
- Each service has a `primaryLinkId`. Every link has its own `probe` config, where null interval/timeout fields mean "use `settings.probe`".
- **Forward compatibility:** every model class extends `Extensible`, which keeps unknown JSON fields. When updating an object, carry its `extra` map over (`ServiceManager.keepExtra`). Schema changes need a new `Migration` and a `schemaVersion` bump.
- Server-managed fields (`icon.cachedFile`) are never taken from clients. Changing an icon's source, value or favicon link clears `cachedFile`, and `IconService` then re-fetches it in the background.

## Patterns
- **All writes** go through `ConfigStore.update(expectedRevision, cfg -> …)`. It copies, mutates, repairs, writes atomically (tmp file + move) and keeps a `.bak`. Throw from the mutator to abort; nothing is saved in that case. `read()` returns a deep copy.
- After each save the store publishes a `ConfigChangedEvent`. Listeners **must not** call `update` synchronously; hand the work to an executor. The event is not published at startup, so use `ApplicationReadyEvent` + `read()` there.
- Optimistic concurrency uses per-resource ETags / `If-Match`: `config/ResourceTags` hashes a resource's user-editable content, excluding server-managed fields like `icon.cachedFile`, and the managers check it inside the `update` mutator. Collection endpoints hash the ordered id list. A stale tag gives 409. `/api/dashboard` exposes the global `revision`.
- Validation uses bean validation on request DTOs plus the `Urls` helpers. Link URLs reject `javascript:`/`data:`/`vbscript:`/`file:`, and probe and icon URLs must be http(s).
- Outbound HTTP uses `java.net.http.HttpClient` with timeouts, size caps and a `Heim/1.0` user agent. A link's `ignoreTls` setting uses a trust-all manager.
- Concurrency uses virtual threads for probes and icon fetches.
- **Security:**
  - There is a single admin, with two toggles: `requireLoginToView` and `requireLoginToEdit`. Both are evaluated live on every request.
  - Edit endpoints also require login whenever view-login is on.
  - `passwordHash` must never appear in a DTO, a log or an export.
  - CSRF uses the `XSRF-TOKEN` cookie, which the client echoes in an `X-XSRF-TOKEN` header on every non-GET request.
  - Unauthenticated requests get 401 JSON, never a redirect.
- A new endpoint must be classified in `security/AccessPolicy` (public / view / edit) and covered in `AuthorizationMatrixTest`.

## Conventions
- Keep controllers thin. Logic goes in `service`/feature packages, and each class has one job.
- Comments are sparse and explain why, not what. No dead code or speculative features.
- Tests use JUnit 5 + AssertJ:
  - Use plain unit tests where possible, with `config/TestStores` for a real store in a `@TempDir`.
  - For API tests use MockMvc `@SpringBootTest` with a temp data dir and `.with(csrf())`.
  - Use okhttp `MockWebServer` for anything that does HTTP. No real network in tests.
- Write commit messages in English and keep them short.

## Frontend
- `src/main/resources/static/heim/` is the design system, copied from the hand-off in `.design/heim-design/` (read its `README.md` and `DESIGN.md`; `.design/` is not committed and stays out of the image). Treat `heim.js`/`heim.css` as a library: class names are a public API for custom CSS. Local changes: in `heim.js`, `Heim.Dashboard` passes `settingsHref`/`loginHref` to the top bar and `loginHref: false` hides "Log in"; in `heim.css`, service cards reserve the description line and pin `.service-card__links` to the bottom, so link chips line up with or without a description.
- `static/js/` is the app, plain ES modules with no build step: `api.js` (fetch, CSRF, If-Match, 401), `status.js` (SSE with polling fallback), `session.js`, `router.js` (hash routes, a fresh `#app` root per view), `ui.js` (dialogs, errors, appearance) and `views/`.
- `js/adapter.js` is the only place where backend JSON and the design's shapes (`heim.d.ts`) meet: link kinds, theme names, probe ↔ health (timeouts are seconds in the API and milliseconds in the UI), LinkStatus → `Heim.applyProbe`, icons (`/icons/<cachedFile>` or initials) and URL/colour sanitizing. Keep the backend contract stable and map there.
- User data never goes into `innerHTML`: build nodes with the Heim factories (they escape) or DOM properties.
